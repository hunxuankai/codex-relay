# 发布计划说明上下文修复设计

## 根因与边界

`App.loadSession()` 把历史 Draft 的 `manifestNotes` 复制到可编辑说明，`preparePlan()` 又把所有非空说明当成人工输入。恢复上一轮 `0.5.1` 后输入 `0.5.2` 时，Rust 收到的仍是旧说明，缺少新目标版本标记，按现有契约拒绝计划。

历史会话、可编辑计划草稿和已经校验的计划是三个不同生命周期：历史会话继续保留在 `ReleaseSession` 中，说明编辑仅服务当前计划上下文，计划必须绑定当前仓库、目标和预检 Latest。

## 组件与数据流

- `App.vue`：继续作为编排入口，绑定仓库、目标和说明；恢复会话仅恢复版本显示，不再把历史 Draft 说明回填为新草稿。
- `RepositorySetupPanel`：继续通过 `v-model` 和 `inspect` / `preparePlan` 事件输入仓库与版本，不增加后端判断。
- `ReleasePlanPanel`：继续展示已校验计划并编辑说明；`regenerate` / `start` 事件和说明一致性门禁不变。
- `useReleaseSession`：继续持有唯一的预检、计划和会话状态，提供显式计划失效动作，复用请求序列抑制过期的预检、计划和恢复响应。
- typed Tauri service → Rust application → `ReleaseNotesService` → candidate transaction 的 DTO、版本校验和安全门禁不变。

## 行为

1. 新建计划不隐式复用历史会话说明；无人工输入时请求后端生成当前正式版本到目标版本的说明。
2. 仓库、目标版本或预检 Latest 变化时，清除旧计划与旧说明；同一上下文内编辑说明后重新生成则保留输入。
3. 已过期的异步响应返回 `null`，不能通过 App 的返回值回填旧说明、路径或版本。
4. 历史 Draft/发布证据继续只来自恢复会话；无需变更 Rust 或落盘 schema。

## 兼容与权衡

清除过期草稿避免自动替换版本字符串，因为替换会让旧更新内容被误当成本次说明。人工重新输入仍由后端校验。保持现有字段和错误码，不扩大控制台的发布权限。

## 回滚与交付

本任务仅变更前端状态及测试、发布契约文档。回滚本次代码提交即可恢复旧控制台逻辑；不执行候选版本写入、真实 Release、Tag 或数据迁移。使用现有 `npm run build:release-console` 生成便携控制台并记录实际产物哈希；若目标 EXE 被锁定则保留失败，使用明确的新交付目录而不终止用户进程。
