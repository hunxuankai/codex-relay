# 改进旧版备份元数据恢复指引

## 目标

当用户从旧版升级到新版后，若历史备份的元数据已不符合当前格式，备份页面应说明
备份为何无法展示，并提供不会误导或损害现有备份的下一步操作，而不是仅显示
“备份元数据格式无效。”。

## 已确认事实

- 用户在安装新版后，于备份页面遇到“备份元数据格式无效。”；此前电脑安装过旧版。
- 后端报错文案位于
  `src-tauri/crates/codex-relay-core/src/services/backup_service.rs:298`。
- 现有前端测试覆盖正常备份元数据展示，但尚未发现无效或旧版元数据的用户恢复
  引导测试。
- 规划与验证不得读取、写入或删除真实 `%USERPROFILE%\\.codex` 或
  `%LOCALAPPDATA%\\CodexRelay` 数据；测试只能使用隔离临时目录和非真实密钥。
- 提交 `3a12680` 为备份新增了 `preferencesExisted` 必填字段；此前写入的元数据
  没有该字段。当前 Rust 反序列化因此拒绝历史备份，而 TypeScript 类型已将同一字段
  视为可选。
- `list_backups` 会因任一目录的元数据解析失败而使整个列表失败；同一方法被
  `cleanup_old_backups` 调用，进而可使后续配置事务在清理阶段回滚。
- 升级安装器按产品契约保留应用数据与备份，因此旧版备份在安装新版后仍会被扫描。
- 恢复历史快照必须保持快照语义：旧备份不含 `provider-preferences.json` 时，恢复会
  将当前该文件恢复为不存在；恢复前的事务备份保留当前配置以供再次恢复。

## 需求

- 确认旧版与新版备份元数据格式的差异、触发无效判定的条件，以及现有备份文件是否
  仍可安全恢复。
- 已知的旧版无版本元数据应在读取时被安全规范化为可恢复备份，且不得原地改写、删除
  或伪造历史元数据。
- 新写入的元数据应具有明确、可演进的格式版本；未知未来版本与真正损坏的 JSON 必须
  被安全地区分，不能伪装成可恢复的历史备份。
- 一份无法读取的备份不得遮蔽其他可恢复备份，也不得阻断新的配置事务或促使清理逻辑
  删除该目录。
- 用户应看到与实际能力一致的下一步：已知旧版备份可恢复；恢复确认须明确其不包含
  命名地址、模型/推理偏好文件且会先备份当前配置；未知或损坏备份应明确保留、不可安全恢复，
  并提供受限的查看元数据途径。
- 任何方案都不得静默删除、覆盖或伪造历史备份；受管配置恢复仍须遵循事务安全约束。
- 用户已确认首期采用保守策略：真正损坏或未知未来格式的元数据只保留并允许受限查看，
  不根据快照文件推断、修复或自动删除元数据。

## 验收标准

- [x] 能复现并精确说明导致“备份元数据格式无效。”的格式或版本条件。
- [x] 形成至少两种可行方案及其兼容性、数据保留、用户操作和实现成本权衡。
- [x] 已知旧版缺少 `preferencesExisted` 的备份会显示为可恢复，且恢复/打开文件/清理
  均不再返回 `INVALID_BACKUP_METADATA`。
- [x] 遇到真正损坏或不受支持的元数据时，其他有效备份仍可列出和恢复；受管配置写入
  不因该目录的保留而回滚。
- [x] 备份页明确区分旧版可恢复备份与不可安全恢复的备份，并提供与状态匹配的可执行
  操作；页面、事件和日志均不泄漏快照内容、绝对路径或密钥。
- [x] 推荐方案明确列出用户看到的状态、可执行操作、失败后的保留行为和测试边界。
- [x] 推荐方案不要求访问真实用户配置或真实备份来验证。
- [x] 用户已确认推荐的恢复策略与允许的自动化程度。

## 范围外

- 不迁移任何真实备份或执行安装包升级。
- 不把不相关的备份系统重构纳入本任务。

## 说明

- 本任务涉及升级兼容性与数据保留，若进入实施，须在启动前补齐 `design.md` 和
  `implement.md`。
