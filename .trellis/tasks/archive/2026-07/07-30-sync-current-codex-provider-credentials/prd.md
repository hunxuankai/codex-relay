# 同步当前 Codex Provider 凭据

## 目标

为当前 Codex 配置提供一个显式同步操作：不切换顶层 `model_provider`，而是把用户选定的 Relay Provider 地址和 API Key 写入当前 `model_provider` 所指向的 Codex Provider 配置，使既有会话在更换上游 Provider 凭据后仍可沿原 Provider 身份继续 `resume`。

## 背景与产品决策

- 用户希望通过界面按钮主动触发，不要求自动同步。
- 同步目标由当前 Codex `config.toml` 的顶层 `model_provider` 参数决定，而不是直接把该参数切换成 Relay Provider 标识。
- 同步内容包括该目标 Provider 的服务地址，以及 Codex `auth.json` 中实际使用的 API Key。
- 核心用户价值是避免因切换 `model_provider` 标识而使不同会话的 `resume` 互不通用。
- 操作入口放在左侧 Provider 列表卡片，与现有编辑、使用和删除动作同一区域，便于快速切换连接。
- 来源凭据固定使用该 Provider 已选中的 Base URL 与 API Key，与现有“使用”动作采用同一来源；需要更换组合时先在详情页调整持久化选择，本操作不提供临时选择器。
- 每次点击卡片入口都先显示确认框；确认摘要包含来源 Provider、已选地址名称、已选密钥名称和目标当前 Provider ID，不显示 URL 全文或 API Key 值，并明确顶层 `model_provider` 不变。
- Relay 必须持久记录当前连接的目标 Provider、来源 Provider 和本次实际应用的地址/密钥条目 ID，不保存第二份 URL 或密钥值；刷新、重启、事务回滚和备份恢复后仍能判定连接来源。
- “恢复”主要指产品内显式恢复：连接覆盖生效时，当前 Provider 卡片提供恢复入口，把被覆盖的 Base URL 和当前认证恢复为该 Provider 覆盖前的自身选择。
- 仅当当前 Provider 覆盖前的地址和密钥均为 Relay 受管条目时允许应用其他 Provider 的连接；未纳管时先通过现有地址管理和密钥导入入口完成纳管。
- 产品面向个人自用可信 Windows 账户，用户接受现有 `providers.json`、`auth.json` 和事务备份中的明文 Key 存储，不要求新增加密能力；连接关系本身只需保存稳定条目 ID，无需再复制一份 Key。
- 卡片采用随状态变化的动作：普通来源显示“仅应用连接”，当前连接且选择未变时显示禁用的“已应用”，来源选择变化后显示“更新连接”，当前 Provider 身份在覆盖期间显示“恢复自身连接”；没有覆盖时当前 Provider 不显示无意义的额外按钮。
- 连接来源与恢复点采用显式持久关系方案：只在 Relay 私有 Provider 元数据中保存目标/来源 Provider 和四个稳定条目 ID；不通过跨 Provider 值匹配推断来源，不保存原始值副本，也不依赖某个事务备份作为产品恢复点。
- 已确认将该关系作为 `provider-preferences.json` v4 的可选顶层状态；旧版 v1/v2/v3 读取时视为没有连接覆盖，继续延迟到下一次成功用户事务再升级写盘。
- 已确认应用与恢复使用两个独立 typed command；前端仅提交来源 Provider ID（恢复时无需来源）和四文件指纹，当前目标、条目 ID、URL 与 API Key 均由 Rust 从最新磁盘状态解析。
- 功能涉及真实用户配置与密钥，所有写入必须遵守现有事务、路径隔离和密钥不出后端的安全约束。

## 需求

- 界面应让用户清楚知道将使用哪个 Relay Provider，以及将覆盖哪个当前 Codex Provider 身份下的运行凭据。
- 卡片按钮文案和视觉层级必须与现有“使用”动作明确区分，不能让用户误以为会切换顶层 `model_provider`。
- 卡片必须同时用文字状态区分“当前身份”“当前连接”和“选择已变化”，不能只靠颜色表达；动态按钮的可访问名称必须与实际动作一致。
- 后端必须投影连接动作枚举、状态文字、禁用原因和安全条目名称；前端只映射显示与事件，不通过 URL、Key 状态或 Provider ID 组合重新推导业务动作。
- 有效连接覆盖是独立的“连接已路由”状态，不得把目标 Provider 误报为外部地址或外部密钥；目标详情必须显示来源和已应用条目名称，且在恢复前锁定其 URL/Key 选择与管理入口，避免破坏恢复点。
- 应用、更新和恢复使用专用的结构化确认对话框；对话框只接收安全摘要，取消时不得调用 command。
- 操作不得接收或保存一次性的 Base URL/API Key 组合，只消费来源 Provider 最近权威状态中的已选项。
- 本操作只改变目标 Provider 块的 `base_url` 与当前 `auth.json`；不得同步来源 Provider 的模型、推理强度、Fast 偏好或改变顶层 `model_provider`。
- 持久连接关系必须与配置和认证写入处于同一事务及备份快照；失败回滚或用户恢复备份时不得留下与文件内容不一致的来源状态。
- 第一次覆盖时固定当前 Provider 覆盖前的地址/密钥条目作为恢复点；覆盖期间从另一个来源再次应用连接时只更新来源和已应用条目，不得把上一层来源变成新的恢复点或形成嵌套恢复栈。
- 显式恢复必须在一个事务中写回固定恢复点对应的 Base URL 与 API Key，并清除连接关系；仍不得改变顶层 `model_provider`、模型、推理强度或 Fast。
- 覆盖期间普通切换到其他 Provider 时，必须先在同一事务恢复原目标 Provider 块的自身 Base URL，再应用新 Provider 的顶层选择和认证并清除关系；不得留下失去恢复点的被覆盖 Provider 块。
- 当前连接使用的来源条目和固定恢复点条目不得在 Relay 内被删除或替换值；必须先更新连接或完成恢复，重命名可保留稳定条目 ID。
- 当前连接来源 Provider 不得删除；存在失效关系时不得应用或更新其他连接，以免覆盖唯一恢复点。
- 读取持久关系时必须重新核对目标 Provider、来源条目和当前配置/认证；外部修改或条目缺失时显示为失效关系，不得在启动、刷新或自检期间自动改写文件。
- 外部修改使目标仍为当前 Provider 时，显式恢复写回目标 URL 与认证；外部修改已把顶层 `model_provider` 切到其他 Provider 时，只恢复原目标 Provider 块的 URL，不覆盖新当前 Provider 的 `auth.json`，然后清除旧关系。
- 固定恢复条目被外部删除或损坏时，一键恢复必须禁用并保留关系及备份入口，不得猜测、静默清除或降级为部分恢复。
- 扩展自检必须识别有效连接覆盖并验证来源条目；有效覆盖不产生“当前地址/密钥未纳管”误报，失效关系产生安全错误但不写盘。当前身份的 Provider 可用性测试在有效覆盖时使用实际路由 URL/Key 和目标自身模型；失效关系时拒绝测试。
- 来源 Provider 和当前 Provider 都必须具有受管的已选 Base URL、受管的已选 API Key 和完整配置；否则卡片覆盖入口禁用并显示安全、可操作的原因。
- 用户确认后，地址与 API Key 必须作为同一个受管操作写入；任一文件写入或验证失败时，不得留下半完成状态。
- `config.toml` 必须保留注释、顺序及未知字段；字段名和 `auth.json` Key 必须以当前项目支持的 Codex 配置契约为准。
- API Key 不得出现在普通前端状态、日志、通知、测试快照、任务材料或 Git 中。
- 缺少当前 `model_provider`、目标 Provider 地址或可用 API Key 时，应阻止操作并提供不泄密的可操作错误。

## 公开接口与可观察行为切片

1. 用户确认把来源 B 的连接应用到当前 A 后，公开 Provider command 只接收 B 的 ID 与最近四文件指纹；后端从最新磁盘状态解析目标 A 和 B 的已选条目，同一事务更新 A 的 `base_url`、当前认证和连接关系。成功后顶层 `model_provider`、模型、推理强度与 Fast 字节保持原值，普通 DTO 不含密钥。Rust 测试使用真实解析器、ProviderService 和临时目录，只在外部文件边界注入故障。
2. A 已使用 B 连接时，来源改选其他条目只改变 B 的预选并使卡片动作变为“更新连接”；确认更新后已应用条目变化而 A 的首次恢复点不变。依次更新到 C 后显式恢复，A 的自身 URL/Key 精确恢复，关系清除。测试不 mock 关系规范化、条目解析或事务验证。
3. A 使用 B 连接期间普通切换到 C，同一公开切换接口先恢复 A 的 Provider 块，再应用 C 的顶层配置与认证并清除关系；任一文件写入或验证失败时，四文件和关系恢复为事务前原始字节。
4. 有效关系使当前身份投影为路由连接，自检验证来源条目且 Provider 可用性测试使用实际路由 URL/Key 与目标模型；外部修改当前 URL、认证或顶层 Provider 后，只读列表和自检把关系投影为失效且不写盘，测试拒绝联网。恢复点完整时显式恢复按当前 Provider 是否仍为 A 选择完整恢复或仅恢复 A 的 Provider 块；恢复点缺失时返回稳定错误并保留关系与备份入口。路径测试使用默认目录哨兵证明真实用户目录递归快照不变。
5. 前端卡片根据后端安全 DTO 显示“仅应用连接”“已应用”“更新连接”或“恢复自身连接”；点击只打开结构化确认框，取消不调用 typed client，确认后 composable 以 busy 和指纹调用一次公开 command，再从后端刷新权威状态。Vue 测试 mock typed client 或 composable，不访问文件系统，也不在 fixture、断言输出或快照中放入真实密钥。

## 验收标准

- [ ] 每个可用 Provider 的左侧列表卡片提供明确的“仅应用连接”类入口；当前操作目标和普通“使用”动作可被文字、键盘与辅助技术区分。
- [ ] 覆盖状态下，目标卡片、当前来源卡片、选择已变化的来源卡片和其他来源卡片分别呈现“恢复自身连接”“已应用”“更新连接”“仅应用连接”，没有覆盖时当前卡片不显示额外动作。
- [ ] 操作不会改变顶层 `model_provider`，但成功后当前 Provider 身份使用所选 Relay Provider 的地址和 API Key。
- [ ] 来源 Provider 有多个地址或密钥时，写入值精确对应其当前已选项；用户在详情页改变选择后，后续卡片操作使用新选择。
- [ ] 点击卡片入口只打开安全确认框；取消时四个受管文件字节不变，确认后才提交事务，确认内容不包含密钥值。
- [ ] 当前 Provider 的实际地址或认证是外部值、缺失值或无匹配受管条目时，所有连接覆盖入口禁用，并引导用户先纳管当前值；不额外保存外部 API Key 副本。
- [ ] 地址和 API Key 要么全部成功，要么经可验证回滚后全部保持原状。
- [ ] 成功后刷新和重启仍能区分“当前 Provider 身份”与“当前连接来源”，并安全显示实际应用的地址/密钥名称。
- [ ] 有效覆盖后的当前身份显示为路由连接，自检与 Provider 可用性测试不误报外部配置；覆盖失效后显示安全原因、拒绝测试且不自动改写四文件。
- [ ] 覆盖期间不能通过目标 Provider 的详情 URL/Key 控件产生半恢复状态；来源未被引用的条目仍可按原规则管理。
- [ ] 当前 Provider 卡片在覆盖期间提供显式恢复并要求确认；恢复成功后精确使用首次覆盖前的自身 URL/Key 条目，连接来源状态消失。
- [ ] 依次把 B、C 的连接应用到当前 A 后执行恢复，结果回到最初 A 的自身选择，而不是回到 B，且全程顶层 `model_provider` 保持 A。
- [ ] A 使用 B 连接期间普通切换到 C 时，同一事务恢复 A 的自身 Base URL、应用 C 的顶层配置与认证并清除关系；以后仍可正常使用 A。
- [ ] 外部修改当前 URL、认证或顶层 Provider 后，连接关系投影为失效且读取路径不写盘；恢复行为按当前 Provider 是否仍为原目标选择完整恢复或仅恢复目标块。
- [ ] 事务失败恢复原始配置、认证和连接关系；恢复包含该关系的备份后，三者重新一致；恢复不含该关系的旧备份仍兼容原有 Provider 语义。
- [ ] 写入保留 `config.toml` 未知内容；`auth.json` 按现有产品契约生成只含当前 `OPENAI_API_KEY` 的规范 JSON。
- [ ] 成功与失败反馈不包含 API Key；测试仅使用安全临时目录和 `test-key-*-not-real` fixture。
- [ ] 对缺失配置、目标不存在、并发外部修改、第二步失败及回滚失败等边界有可观察且可测试的结果。

## 范围外候选

- 自动随偏好变化持续改写 Codex 配置。
- 联网校验 API Key 或服务可用性。
- 改变 Codex 会话文件或迁移既有会话元数据。
