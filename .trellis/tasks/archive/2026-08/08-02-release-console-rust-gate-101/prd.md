# 诊断发布控制台 Rust 门禁 101

## 目标

确定发布控制台在准备 `0.5.0` 候选后执行 `release-console-rust-tests` 时，Cargo 以退出码
`101` 失败的直接原因，并向维护者说明失败边界与当前仓库安全状态。

## 已确认事实

- 失败会话 `release-20260802084619-0000000000000002` 持久化为
  `phase=failed`、`failure.phase=localChecks`、`stepId=release-console-rust-tests`。
- 该步骤执行固定命令
  `cargo test --manifest-path src-tauri/Cargo.toml -p codex-relay-release-console`。
- 控制台从 `artifacts/release-console/CodexRelayReleaseConsole.exe` 运行，已排除旧的
  `dist` 输出树自锁故障。
- 候选失败后六个计划文件已回滚，当前工作区干净，未创建候选提交、未推送、未触发远端 Run。
- 在回滚后的干净仓库中，以成对安全 Relay 临时路径复跑同一命令，110 个测试通过、
  1 个按设计忽略，退出码为 0；因此失败只在候选文件临时生效或当时运行环境中出现。
- 在隔离 worktree 中恢复完整 `0.5.0` 六文件候选后，编译阶段和完整测试同样通过。
- 通过临时启动器复用生产 `SafeProcessRunner` 的外层 Windows Job 与过滤环境后，完整候选测试
  仍退出 0；现有持久化会话未保存原始 stdout/stderr 或失败测试名称。
- 在原仓库路径和原失败缓存中临时重放完整候选也退出 0，随后六文件哈希逐项恢复；恢复版本的
  固定命令再次通过。因此原 `101` 不是稳定的版本切换或 target 缓存错误。

## 需求

- 只使用仓库、Git 元数据和安全临时路径进行诊断，不读取或写入真实 `.codex` 与
  `%LOCALAPPDATA%\CodexRelay`。
- 在隔离副本中重建控制台生成的 `0.5.0` 六文件候选，复跑相同 Cargo 门禁并保留首个具体错误。
- 区分 Cargo 通用退出码 `101`、具体编译/链接/测试失败，以及控制台完成的候选回滚行为。
- 本任务仅诊断并解释原因；未经用户要求，不修改产品实现或发布流程。

## 验收标准

- [x] AC1：证据将失败收窄到测试执行阶段，并明确记录因原始输出未持久化而无法唯一还原具体用例。
- [x] AC2：能够说明回滚后和隔离候选复跑均通过，原 `101` 属于当时的一次非确定性运行时失败。
- [x] AC3：确认当前工作区、候选提交、推送和远端 Run 的实际状态，不夸大成功或失败范围。
- [x] AC4：所有诊断测试均使用安全临时用户/Relay 路径，且隔离副本和临时目录完成清理。

## 范围外事项

- Windows Sandbox、真实安装、签名、升级、卸载和数据保留验证。
