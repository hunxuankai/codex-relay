# v0.3.0 发布设计

## 发布边界

本任务只在现有 GitHub Actions 发布链路上生成新版本，不改变应用架构、updater 信任根、
NSIS 模板或历史清理算法。权威应用版本来自 `package.json`，Cargo 包、锁文件和发布结构
测试跟随同步；`tauri-action` 依据该版本创建 `v0.3.0` Tag、Draft Release 和 updater
资产。

## 状态流

1. 本地候选：同步版本与最终说明，运行完整检查和无私钥普通构建。
2. 远端候选：提交并推送到 `main`，固定候选提交 SHA。
3. Draft：手动触发发布工作流，等待其在同一提交上完成检查与签名资产构建。
4. 审计：通过 GitHub API 读取 Draft 元数据和资产，下载到系统临时目录核对大小、
   SHA-256、`latest.json`、独立 `.sig` 与清单内联签名。
5. 公开：仅在审计通过后把 Draft 公开；再次读取 Latest 与公开资产，确认没有漂移。
6. 清理：等待独立清理工作流，确认只保留 `v0.3.0` Release/Tag。
7. 升级：使用公开前保存的 `v0.2.1` 安装器，在安全隔离环境验证应用内升级；该证据
   与构建、签名和公开状态分别记录。

## 安全与数据边界

- GitHub 认证只由 `gh` 和 Actions 自身凭据处理；任务、命令输出和日志不包含 Token、
  私钥、密码或完整认证文件。
- 所有下载与 Sandbox staging 位于系统临时目录真子路径；不得位于仓库、真实 Codex
  配置目录或真实 Relay 应用数据目录，也不得经过 reparse point。
- Sandbox fixture 只使用 `test-key-*-not-real`，两项 Relay 路径覆盖必须成对设置。
- 远端历史 Release/tag 删除只属于公开资产保留策略，不触及本机配置、日志、备份或密钥。

## 兼容性与回滚

- `v0.3.0` 严格高于 `v0.2.1`，现有 updater 可以通过固定 Latest 清单发现它。
- Draft 审计失败时删除错误 Draft，修正源码后使用新提交重新运行；不公开错误资产。
- 发布工作流失败时保留失败步骤和提交证据，不以相同提交盲目重跑。
- 正式公开后不替换同版本资产；若发现缺陷，发布更高 SemVer 修复版本。
- 清理工作流部分失败时保留真实列表，通过其手动入口安全重试，不使用通配符删除。
